# FightAI 기술 문서

*2D MuJoCo 랙돌 격투 에이전트 — 설계, 리워드 셰이핑 히스토리, 진단 방법론*

## 1. 프로젝트 개요

MuJoCo 물리 시뮬레이션 위에서 동작하는 2D 랙돌(ragdoll) 격투 에이전트를 PPO(Proximal Policy
Optimization)로 학습시키는 프로젝트다. 에이전트 'a'는 셀프플레이(self-play) 방식으로, 주기적으로
스냅샷을 갱신하는 자기 자신의 과거 정책 'b'와 대전하며 학습한다. 관절 힘/접촉력 기반의 물리적으로
사실적인 데미지·스태거·낙상 시스템 위에 격투 게임 특유의 보상 구조(넉다운, KO, 헤드샷·킥 보너스
등)를 얹은 것이 핵심 설계다.

- 물리 엔진: MuJoCo (mj_step, mj_contactForce 기반 접촉력 계산)
- 강화학습: Gymnasium 커스텀 환경 + stable-baselines3 PPO, SubprocVecEnv 병렬 8개 환경
- 학습 방식: 셀프플레이 — 주기적으로 정책 스냅샷을 얼려서 상대 'b'로 사용, 좌우 반전(mirror)된
  시점으로 관측/행동 변환

## 2. 아키텍처

### 2.1 물리 모델 (`models/fighter2d.xml`, `scripts/build_model.py`)

각 파이터는 몸통/머리/양팔/양다리로 구성된 2D 랙돌이며, root_x·root_z(슬라이드 조인트)와
root_ry(힌지)로 XZ 평면에 구속된다. 관절 9개(head, shoulder_r/l, elbow_r/l, hip_r/l, knee_r/l)는
모두 motor 액추에이터로 구동된다. fighter2d.xml은 build_model.py가 생성하므로, 모델을 직접
수정하지 말고 항상 build_model.py를 고쳐서 재생성해야 한다 (한 번 XML을 직접 손으로 고치고
생성기를 안 고쳐서 root_x 모터 정의가 스크립트와 어긋난 적이 있었다).

- root_x는 직접 액추에이션 — 걷기를 처음부터 학습시키는 대신 이동 자체를 RL 밖으로 빼서, 정책이
  진짜 격투 의사결정(간격, 타격, 방어)에 집중하게 함
- root_ry(몸통 피치)는 RL이 직접 제어하지 않고, 항상 켜져 있는 PD 밸런스 보조가 담당 (2.3절)
- 무기 geom: 주먹(forearm_r/l), 발(shin_r/l) / 타겟 geom: head, torso, thigh+shin(leg)
- shin 끝에 a_foot_r/l, b_foot_r/l site를 추가해 두 파이터의 발 사이 거리(간격 페널티 계산용)를 추적

### 2.2 Gymnasium 환경 (`scripts/env.py` — Fighter2DEnv)

행동 공간: `Box(-1, 1, shape=(10,))` = [root_x thrust, head, shoulder_r, elbow_r, shoulder_l,
elbow_l, hip_r, knee_r, hip_l, knee_l]

관측 공간: a/b 각각의 qpos+qvel(12차원 관절 상태) + 상대 위치·체력·스태거 등 부가 정보 6개

매 step은 FRAME_SKIP=4번의 mj_step으로 구성된다. step()에서 접촉력 기반 데미지 계산, 체력/스태거/
다운 상태 갱신, 보상 항목 합산, 종료 조건 판정을 수행하고 info에 reward_breakdown(항목별 보상)을
담아 반환한다.

### 2.3 밸런스 보조 (물리, 리워드 아님)

root_ry는 RL 행동 공간에 없는 전용 모터로, 매 서브스텝마다 PD 제어(BALANCE_KP=25, BALANCE_KD=10)로
직립 방향으로 되돌린다. 직접 시뮬레이션으로 검증한 결과, 수동적인 stiffness만으로는(200까지
올려봐도) 넘어지는 것을 막지 못했다 — 서 있는 이족보행체는 본질적으로 역진자(inverted pendulum)라
능동 제어가 필요하다는 물리적 한계였다. 이 PD 보조 도입 후 넉다운 회복 성공률이 0%에서 약 30~50%로
개선됐다.

### 2.4 스태거 (다리 피해 → 자세 손실)

다리 피해가 누적되면 stagger 값이 올라가고, stagger가 높을수록 액추에이터 권한이 줄고
(STAGGER_CONTROL_LOSS=0.6) 제어 노이즈가 커진다(STAGGER_NOISE_STD=0.4). 단순 페널티가 아니라
'다리를 잃으면 실제로 서 있기 어려워지는' 물리적 결과로 구현했다. 매 스텝 STAGGER_DECAY=0.94로
서서히 회복된다.

### 2.5 팔 힘-각도 커브 (근육형 force-length curve)

관절 중간 지점에서 최대 토크(100%), 완전히 펴거나 접은 극단에서 최소 토크(ARM_MIN_POWER=0.4)로
떨어지는 sin 곡선을 팔 4관절(shoulder_r/l, elbow_r/l)에 적용해, 실제 근육의 힘-길이 관계를
거칠게나마 흉내냈다. 다리(hip/knee)에는 아직 이 커브가 적용되어 있지 않다 — 회전형 킥에 대한 논의
(6절 참고) 이후 다리 힘 커브 적용 여부는 아직 미결정.

### 2.6 셀프플레이 미러링 (`scripts/env.py` — `_obs_for_b`, `_action_mirror`)

'b'는 자기 자신의 시점에서 관측을 받아야 학습이 의미가 있다. 두 파이터는 서로 반대쪽에서
시작하므로, 'b'의 관측/행동은 'a' 시점 기준 좌우 반전(X → -X)이어야 한다. 처음에는 root_x만
반전시켰으나(위치 이동만 뒤집으면 된다는 가정), 이는 물리적으로 틀렸다 — 관절 회전(root_ry 포함,
9개 관절 전부)도 Y축 회전이므로 반사 변환에서 부호가 뒤집혀야 한다(축 벡터의 반사 변환 규칙). 이
누락은 실제로 측정 가능한 손실로 나타났다: 수정 전 40 에피소드 기준 a의 데미지량 658.9 대비 b는
116.8에 불과했고, 전체 반전 수정 후 175.8로 개선됐다.

```
_qpos_mirror = [-1, +1, -1, -1, ..., -1]  # root_x, root_z, root_ry, <9 joints>
_action_mirror = [-1, -1, ..., -1]          # root_x thrust + 9 joint torques, 전부 반전
```

### 2.7 학습 파이프라인 (`scripts/train_selfplay.py`)

PPO.load()로 체크포인트에서 이어 학습한다. `--refresh-interval`(기본 250,000 스텝)마다 현재 정책을
스냅샷으로 저장하고, 모든 병렬 환경의 상대 'b'를 그 스냅샷으로 교체한다(`env_method('set_opponent',
...)`). CheckpointCallback으로 `--save-freq`(기본 25,000 스텝)마다 autosave/에 저장하므로 크래시가
나도 진행 상황을 거의 잃지 않는다.

- **OpponentRewardCallback**: 'b'의 미러링된 에피소드 보상(reward_b)을 rollout/b_ep_rew_mean으로
  로깅 — 'a'가 최근 자기 자신보다 실제로 나아지고 있는지 보여주는 지표 (리워드 함수 자체가 바뀌면
  절대값은 의미 없어지지만, a-b 격차는 안정적인 진행 지표)
- **BreakdownCallback**: reward_breakdown의 7개 항목(strike/effort/jerk/engage/down/
  knockdown_entry/terminal)을 각각 rollout/r_*로 로깅 — 전체 보상 변화가 어느 항목 때문인지 바로
  추적 가능
- `scripts/selfplay_loop.sh [rounds] [timesteps_per_round] [refresh_interval]`: 이전 라운드의
  최신 체크포인트를 자동으로 찾아 이어서 여러 라운드를 반복 실행하는 래퍼 스크립트

### 2.8 대시보드 (`scripts/dashboard.py` + `dashboard_index.html`)

외부 의존성 없는 순수 Python http.server 기반 로컬 웹 대시보드(포트 8787). 터미널 없이 학습/뷰어
실행을 제어하고 진행 상황을 그래프로 볼 수 있다.

- 학습 로그를 파싱해 rollout 테이블 전체 이력을 그래프로 표시 (최대 300포인트로 다운샘플)
- 차트 2종: 전체 보상(ep_rew_mean, b_ep_rew_mean, ep_len_mean)과 항목별 breakdown(r_strike 등),
  스케일이 달라 분리
- r_effort/r_jerk/r_engage는 구조적으로 항상 음수인 '비용' 항목이라, 실제 학습 리워드 계산은 그대로
  두고 화면 표시에서만 부호를 양수로 뒤집어 '낮을수록 좋음' 비용으로 보여줌 (ALWAYS_NEGATIVE_KEYS)
- 체크포인트 목록(top-level + autosave 병합, 최신순, 페이지네이션 지원 — 페이지당 20개, 최신이
  항상 1페이지), 학습/뷰어 시작·중지 버튼, 학습 방식 라디오(스크립트 상대/셀프플레이/paired/리그전),
  셀프플레이 옵션(refresh interval, ent_coef 오버라이드), '최신 스냅샷 보기' 버튼, 미러 매치 뷰어 토글
- **대결 지표 패널**: 임의의 두 체크포인트를 Fighter A/B로 골라 실제 N판을 붙여보고(내부적으로
  `matchup_eval.py`를 서브프로세스로 실행) 승패·종료 사유별 횟수·평균 체력/길이를 즉시 보여줌 —
  터미널에서 diag_engage.py를 수동으로 돌리지 않아도 UI에서 바로 대결 실측 가능
- 총 보상/breakdown 차트는 x축을 raw total_timesteps가 아니라 **데이터 포인트 순번**으로 그림 —
  로그 파일 하나에 서로 다른 학습 실행(예: 리그전의 P1/P2)이 섞여 있으면 각자의 total_timesteps
  카운터가 라운드마다 리셋돼서 zig-zag로 겹쳐 그려지는 문제가 있었음

### 2.9 시각 피드백 (`scripts/watch.py`)

MuJoCo 인터랙티브 뷰어에 체력바(각 파이터 머리 위, 남은 체력 비율만큼 폭이 줄어듦)와 피격
이펙트(맞는 순간 확장/페이드되는 스파크)를 viewer.user_scn에 직접 그려서 오버레이한다.
`--opponent` 플래그로 셀프플레이 미러 매치를 관전할 수 있다.

### 2.10 진짜 동시 셀프플레이 (`scripts/selfplay_vec_env.py`, `train_selfplay_paired.py`)

기존 train_selfplay.py 방식은 'a'만 계속 그래디언트로 학습되고 'b'는 주기적으로 갱신되는 얼려진
스냅샷이었다. 이 구조 자체가 'a'는 항상 지금 막 탐험 중이고 'b'는 탐험이 멈춘 과거 시점이라는
비대칭을 내재하고 있다는 게 4절의 조사로 드러나면서, 'b'도 얼리지 않고 매 스텝 같은 살아있는
정책으로 직접 플레이하게 만드는 진짜 동시 셀프플레이 구조를 새로 구현했다.

`PairedSelfPlayVecEnv`는 N개의 물리 MuJoCo 시뮬레이션(워커 서브프로세스)을 SB3에는 2N개의 학습
슬롯으로 노출한다 — 슬롯 2i는 물리 환경 i의 'a' 시점, 슬롯 2i+1은 같은 매치의 'b' 시점. 매 스텝
물리는 한 번만 진행되고(`env.step()`에 새로 추가한 `b_full_action` 파라미터로 'b'의 행동을
외부에서 직접 주입), 양쪽 시점의 (관측, 행동, 보상) 전부가 같은 PPO 롤아웃 버퍼에 들어가 같은
정책을 업데이트한다. 더 이상 상대 스냅샷 갱신이라는 개념 자체가 없다 — 'b'가 항상 정확히 지금 이
순간의 'a'이기 때문이다.

구현 중 두 가지 순수 로깅 버그를 발견해 수정했다 (둘 다 학습 자체엔 영향 없음, 모니터링만 왜곡됨):

- SB3가 기대하는 `info["episode"]` 키를 채워주지 않아 ep_rew_mean/ep_len_mean이 갱신되지 않고
  고정값만 반복 출력됨 — Monitor 래퍼와 동등한 에피소드 리턴/길이 추적을 워커에 직접 구현해 해결.
- down/terminal/balance/ground/knee/strike는 전부 a-vs-b 부호 있는 제로섬 항목인데, 이제 a슬롯(+X)과
  b슬롯(-X)이 같은 통계 풀에 들어가 평균 내면 수학적으로 항상 0으로 상쇄됨 — 버그가 아니라 설계상
  당연한 결과였지만, 그러면 모니터링 가치가 없어져서 절댓값으로 집계하도록 BreakdownCallback을 수정.

### 2.11 리그 셀프플레이 (`scripts/train_league.py`, `scripts/selfplay_league_loop.sh`)

paired self-play까지도 a/b 비대칭을 완전히 해결하지 못한 근본 원인이 물리적인 것(4절, 3절 19번)
으로 밝혀진 뒤, "공유 정책 하나가 양쪽 다 잘해야 한다"는 요구 자체를 버리고 **P1('a' 전용)과
P2('b' 전용)를 완전히 별도의 모델로 학습**시키는 방식으로 전환했다.

`Fighter2DEnvForB` (env.py)는 Fighter2DEnv를 상속해 RL 행동 공간이 'b'를 제어하도록 뒤집은
래퍼다 — reset()/step()이 `_obs_for_b()`/미러링된 액션을 다루고, 'a'는 `set_opponent()`로 로드한
얼려진 스냅샷이 담당한다(기존 train_selfplay.py의 'a' 전용 구조와 정확히 대칭).

`train_league.py --side {a,b}`는 어느 쪽을 학습할지 고르고, `--init-from`(이 쪽 정책 자체)과
`--opponent-from`(고정된 상대, 이번 라운드 내내 안 바뀜)을 독립적으로 지정할 수 있다 — 기존
train_selfplay.py와 달리 상대가 자기 자신의 과거 스냅샷이 아니라 완전히 다른 모델이기 때문.

`selfplay_league_loop.sh [rounds] [timesteps] p1_init p2_init`가 라운드마다 P1↔P2를 번갈아
학습시킨다. 처음 구현에서는 매 라운드 항상 P1이 먼저 학습했는데, 이러면 P2는 항상 방금 갱신된
최신 P1을 상대로 준비하고 P1은 한 라운드 뒤처진 P2만 상대하게 되어 **순서 자체가 매 라운드 P2에게
구조적 이득을 주고 누적**됐다(3절 22번). 라운드 홀짝에 따라 어느 쪽이 먼저 학습할지도 번갈아주도록
수정.

## 3. 리워드 셰이핑 히스토리

리워드 함수는 추측이 아니라 매번 관찰된 구체적 실패 양상에 대응해 반복적으로 수정됐다. 타임라인
순으로 정리하면:

**1. root 직접 액추에이션 + 스크립트 상대**
처음부터 걷기를 학습시키자 시작 거리가 최대 팔 리치를 넘어서 접촉 자체가 발생하지 않았다. root_x
직접 제어로 즉시 해결.

**2. 동시 낙상(mutual fall) 페널티**
넉다운급 타격을 주고받으며 둘 다 쓰러지는(에피소드 즉시 종료) 교환이 보상상 중립이라, 에이전트가
신중한 공방 대신 한 방 노리는 러시를 학습했다. MUTUAL_FALL_PENALTY=20 추가.

**3. 회복 가능한 넉다운**
쓰러짐이 즉시 에피소드 종료였던 탓에 최대 가능 지속시간의 약 9%에서 경기가 끝났다.
DOWN_RECOVERY_STEPS(~3초) 안에 일어나면 계속 진행되도록 변경.

**4. 넉다운 진입 페널티**
회복이 가능해진 뒤에도 여전히 '한 방 크게 맞고 빨리 일어나기'가 기대값상 이득이었다 (캡 걸린 한
방이 8~19 보상인데 반해 빨리 일어나는 비용은 1~3에 불과). 쓰러지는 순간 일회성 페널티
KNOCKDOWN_ENTRY_PENALTY=30 추가.

**5. 데미지 보상 스케일 축소 → 재상향**
접촉력 기반 조밀한 보상이 너무 커서 '세게 한 대 때리기'가 '실제로 넉다운/KO를 만들기'와 경쟁할
정도였다. DAMAGE_REWARD_SCALE을 0.35까지 낮췄다가, 이후 '접촉 없음' 에피소드의 80%가 사실 조기
자기 붕괴(self-destabilization) 때문이지 공격 의지 부족이 아니라는 게 밝혀지며 그 판단이 다시
열려 0.7 → 1.0(무보정)으로 재상향.

**6. 자세 페널티 — 추가했다가 두 라운드 후 제거**
쓰러진 건 아니지만 눈에 띄게 웅크린/불안정한 자세로 있는 스텝이 전체의 약 24%로 측정돼 페널티를
추가했으나, 킥 보너스와 원터치원히트 수정이 근본 원인(다리의 공격적 용도 부재, 쓰러진 상대 옆에
붙어서 파밍하는 유인)을 해소하자 다시 제거. 단독으로는 정당한 방어 자세/킥 준비 동작과 나쁜 자세를
구분할 수 없었다.

**7. 킥 보상 보너스 (KICK_REWARD_BONUS=2.0)**
킥이 물리적으로 펀치보다 약간 강함에도(다리 질량·힙 액추에이터 게인이 더 큼) MAX_STEP_DAMAGE 캡
때문에 이 차이가 보상에 전혀 드러나지 않아, 균형을 거는 위험을 감수할 이유가 없었다. 신 랜딩
데미지에 보상 전용(체력 계산엔 영향 없음) 2배 배율 부여.

**8. 원터치원히트 (one-touch-one-hit)**
쓰러진 상대 위에 계속 붙어 있으면 매 프레임 캡 데미지를 반복해서 넣을 수 있어 0.25초만에 체력
100을 다 깎는 파밍 버그가 있었다. 새로운 무기-타겟 접촉 쌍에만 데미지를 인정하도록 수정.

**9. EFFORT_COST 버그 (가장 큰 발견)**
자기 붕괴(접촉 없이 스스로 넘어짐)를 잡으려고 EFFORT_COST를 0.01 → 0.05 → 0.15까지 세 차례
올렸으나, 매번 mean|action|을 직접 측정해도 행동에 아무 변화가 없었다. reward_breakdown 도구로
확인해보니 EFFORT_COST가 에피소드당 약 -250, 즉 전체 음수 보상의 75% 이상을 차지하면서도 행동에는
아무 영향이 없이 실제 전투 신호(+5/에피소드)를 완전히 압도하고 있었다. 0.01로 되돌리자 에피소드
보상이 약 -300 → -54.3으로, strike 보상이 +5 → +36으로 급격히 개선됐다.

**10. 셀프플레이 완전 미러링 수정**
root_x만 반전하던 것을 관절 회전까지 포함한 전체 좌우 반사로 수정 (2.6절 참고).

**11. 팔 힘-각도 커브**
관절 각도에 따라 팔 토크를 차등화해(2.5절) 완전히 뻗거나 접은 팔의 타격이 더 약하게 만들었다.

**12. 접촉력→데미지 스케일 재조정 (FORCE_TO_DAMAGE 0.4 → 0.007)**
'회전형 킥이 더 높은 점수를 받아야 하지 않나'는 질문에서 출발한 진단(diag_kick_cap.py)으로, 실제
펀치/킥 접촉의 94~97%가 이미 MAX_STEP_DAMAGE=8.0 캡을 훨씬 초과하는 힘을 내고 있어서 약하게 스친
타격과 회전을 실어 강하게 꽂은 타격이 보상상 완전히 동일하게 처리되고 있었음을 발견했다.
FORCE_TO_DAMAGE를 재조정해 캡이 상위 ~10%의 타격에서만 걸리도록 바꿔, 타격의 실제 파워 차이가
데미지/보상에 반영되게 함.

**13. 미러 증강 (A_MIRROR_AUGMENT_PROB=0.5)**
미러 self-play 매치에서 'a'가 60~97%의 확률로 자기 붕괴하며 넘어지는 반면 'b'는 거의 그러지
않는(예: 57:3) 극단적 비대칭을 발견. 좌우 위치를 서로 바꿔도, MuJoCo 컴파일 시 body 순서를
바꿔도, a/b를 완전히 같은 코드 경로로 호출해도 결과가 똑같아서 물리/코드 버그가 아니라 '신경망이
자기 자신의 미러 변환 결과에 대해 실제로는 동등하게 행동하지 않는다'는 결론에 도달. 원인은 'a'만
그래디언트로 학습되고 'b'는 얼려진 스냅샷이라, 미러링된 관측 프레임이 한 번도 직접 최적화된 적이
없어서였다. 'a' 자신도 무작위로 절반의 에피소드는 미러 프레임으로 플레이하게 강제해 그 프레임에도
직접 그래디언트가 흐르게 함.

**14. balance 페널티 (BALANCE_FREE_ZONE / BALANCE_PENALTY_SCALE)**
낙상 관련 항목(down/knockdown_entry)이 전부 '이미 넘어진 뒤' 사후 페널티라, 균형 유지에 대한
조밀하고 즉각적인 신호가 없었다. root_ry(몸통 기울기) 자체에 페널티를 걸되, 평소 흔들림(~0.02-0.03
rad)까지 벌점화하면 EFFORT_COST와 같은 함정(늘 존재하는 잡음에 벌점을 줘서 실제 위험 신호가
묻힘)에 빠지므로, 측정으로 확인한 free zone(0.15 rad) 밖으로 벗어난 '위험한' 기울어짐에만
제곱으로 세게 벌점을 주도록 설계.

**15. 발 접지 보상 / 무릎 착지 페널티 (GROUND_CONTACT_SCALE / KNEE_CONTACT_PENALTY)**
실제 격투가가 안정성을 위해 발을 땅에 붙이고 서 있는 것과 같은 원리로, 발이 지면에 닿아 있는
시간에 비례해 보상하고, 무릎이 지면에 닿으면(다리가 무너지는 신호) 세게 벌점을 주는 항목을 추가.
새 geom 없이, shin 캡슐이 지면과 접촉한 지점이 무릎 쪽(shin 몸체 자신의 원점)에 가까운지 발
쪽(foot site)에 가까운지로 두 상황을 구분해 구현.

**16. '처음부터 학습' 대조 실험**
오래 학습해 굳어진 나쁜 습관 때문에 비대칭이 생긴 게 아닌가 하는 가설을 검증하기 위해, 예전
체인의 가중치를 전혀 안 섞고 랜덤 초기화부터(train.py, --resume-from 없이) 완전히 새로 학습한
뒤 셀프플레이에 투입. 결과: 똑같은 비대칭이 1라운드부터 재현됨 (52~53:7 수준). 이로써 '오래된
습관 탓'이라는 가설은 폐기되고, 원인이 self-play 구조 자체에 있다는 확신이 커짐 — 다만 이후 진짜
원인은 '얼려진 상대'보다 더 근본적임이 17번 항목에서 드러난다.

**17. 진짜 동시 셀프플레이 (paired self-play, 2.10절 참고)**
'a'만 학습하고 'b'는 얼려지는 구조 자체를 없애고, 두 시점 다 같은 살아있는 정책이 동시에 플레이하며
둘 다 그래디언트를 받도록 아키텍처를 새로 구현. 도입 초반(수백만 스텝)엔 비율이 47:13(78:22)까지
개선되는 것처럼 보였으나, std가 0.044까지 완전히 수렴할 때까지(2억 스텝 이상) 학습을 더 진행하자
55:5(92:8)로 원래의 나쁜 비율로 되돌아왔다. 즉 초반의 개선은 수렴 과정의 일시적 현상이었지, 안정된
해결이 아니었다.

**18. 자발적 대칭 깨짐 (spontaneous symmetry breaking) — 중간 결론**
환경/물리는 완벽히 대칭이지만, 이를 학습하는 신경망은 '원본 상태에 대한 반응'과 '미러링된 상태에
대한 반응'이 서로 미러 관계여야 한다는 제약을 전혀 받지 않는다. 랜덤 초기화의 미세한 비대칭이
on-policy 학습의 자기강화 루프를 통해 점점 굳어지는 것으로 보인다는 가설 — 다만 이건 '왜 신경망이
그 제약을 스스로 못 만족하는가'까지였지, '애초에 물리적으로 그 제약을 만족하는 게 가능한가'는
확인 전이었다. 19번 항목에서 후자가 사실은 불가능했다는 게 드러난다.

**19. 순수 물리 실험으로 진짜 원인 규명**
정책도, 미러링 코드도 전혀 없이 그냥 관절에 고정된 상수 토크(+0.3 대 -0.3, 정확히 미러링된 값)만
주고 balance assist만 켠 최소 재현 실험을 만들었다. 결과: **부호만 다르면 100% 재현/역전**됐다 —
a 관절에 +0.3, b 관절에 -0.3을 주면 a가 넘어지고, 반대로 주면 b가 넘어진다. 좌우 위치를 바꿔도,
MuJoCo 컴파일 순서를 바꿔도 무관하게 오직 부호로만 결정됐다. 즉 **이 랙돌은 관절에 양수 토크를
주는 것과 음수 토크를 주는 것이 물리적으로 똑같이 안정적이지 않다** (무릎/팔꿈치가 range의 끝
지점(완전히 편 상태)에서 시작하는 구조와 관련된 것으로 추정). 미러링은 정의상 "한쪽은 원본 부호,
다른 쪽은 반전된 부호"를 강제하므로, 신경망이 관절 값에 대해 어느 쪽으로든 아주 조금만 편향을
가지면 — 그 편향이 어떻게 생기든(자발적 대칭 깨짐이든 다른 이유든) — 미러링 때문에 한쪽은 항상
안정적인 부호를, 다른 쪽은 항상 불안정한 부호를 받게 된다. 좌표계를 아무리 잘 대칭화해도(중심을
0으로 두고, 관절 부호까지 정확히 반전해도) 이 물리적 비대칭 자체는 좌표계로 해결할 수 있는 문제가
아니라는 게 최종 결론.

**20. equivariant 정책 아키텍처 시도**
그래도 "구조적으로 대칭을 보장"하는 마지막 시도로, f(x) = 0.5 · (g(x) + mirror_action · g(mirror_obs · x))
형태로 정책망을 감싸는 MirrorEquivariantPolicy를 구현 (`scripts/equivariant_policy.py`). 이는 Z2
반사군에 대한 표준 대칭화(Reynolds operator) 구성으로, obs_mirror·action_mirror가 둘 다 자기 역원
(±1 대각행렬)이라는 성질 덕분에 f(mirror(x)) == mirror(f(x))가 대수적으로 항상 성립함을 직접
증명·검증(오차 0.0)했다. 기존 체크포인트에서 가중치를 이식(learnable parameter 추가 없음, 순수
forward pass 재구성)해 paired self-play로 재학습. 초반엔 반영이 잘 안 됐고(8192스텝 스모크
테스트에선 변화 없음), 처음부터 새로 학습시켜도 여전히 55:5 → 54:6 등 비슷한 비율이 재현됐다.
19번 항목의 결론과 종합하면 — 함수 자체는 증명 가능하게 대칭이어도, **그 함수가 두 프레임 모두에
대해 "실제로 잘 작동"하도록 만드는 것은 물리적으로 불안정한 부호 쪽을 정책이 학습해야 하는, 훨씬
어려운 문제**로 보인다.

**21. 결론: 두 개의 전용 모델로 전환 (리그 셀프플레이)**
공유 가중치 하나가 양쪽 프레임 모두에서 똑같이 잘해야 한다는 요구 자체를 포기하고, **P1('a' 전용)과
P2('b' 전용)를 완전히 별도의 모델로 학습**시켜 서로의 최신 스냅샷을 상대로 번갈아 학습하는 방식
(AlphaGo류 리그 self-play)으로 전환 (2.11절 참고). 각자 자기 역할만 잘하면 되므로, 지금까지 계속
발목을 잡았던 "미러 프레임 일반화" 문제 자체가 사라진다.

**22. 리그 학습 순서 편향 버그**
처음 구현한 리그 루프는 매 라운드 항상 P1이 먼저, P2가 나중에 학습했다. 이러면 P2는 항상 "방금
갱신된 최신 P1"을 상대로 준비할 기회를 얻고, P1은 항상 "한 라운드 전의(약간 뒤처진) P2"만 상대할
수 있어서 — 순서 자체가 매 라운드 P2에게 구조적 이득을 주고, 이게 상쇄되지 않고 라운드마다
누적됐다(실측: 87:13 → 97:3로 점점 벌어짐). 라운드 홀짝에 따라 어느 쪽이 먼저 학습할지도 번갈아
주도록 수정한 뒤로는 격차가 다시 좁혀지기 시작했다(97:3 → 82:18 → 80:20, 계속 개선 중). '이미 너무
벌어져서 못 좁히는 거 아니냐'는 우려도 있었지만, 순서만 고쳐도 자연스럽게 좁혀지는 걸 보면 그
정도로 굳어진 상태는 아니었던 것으로 보인다.

> **재사용할 만한 진단 방법론**: 이 수정들 대부분은 뷰어를 눈으로 보고 감으로 판단한 게 아니라,
> 체크포인트를 로드해 N 에피소드를 돌리고 접촉력 분포·자세 높이 히스토그램·에피소드당 넉다운
> 횟수·정확한 타격 시점 같은 구체적인 수치를 측정하는 짧은 스크립트를 작성해서 나왔다. 뷰어는
> '뭔가 이상하다'는 걸 알아채는 데는 좋지만, '왜' 이상한지는 이런 진단 스크립트가 짚어준다.
> 19번 항목처럼 정책조차 없이 순수 물리만으로 최소 재현을 만드는 것도 강력한 방법이었다 — 변수를
> 하나씩 지워나가다 결국 "정책, 학습, 미러 코드 전부 빼고 부호 하나만 바꿔도 재현된다"는 데
> 도달하면서, 문제가 있는 레이어를 (RL/신경망이 아니라) 물리 시뮬레이션까지 좁힐 수 있었다.

## 4. Self-play a/b 비대칭 심층 조사

미러 self-play 매치에서 'a'가 압도적으로 더 자주 넘어지는 현상(예: 60판 중 52~58판)을 코드
버그로 의심하고 체계적으로 소거법 조사를 진행했다. 매번 40~60 에피소드 기준으로 재현되는지 직접
측정했다:

| 가설 | 테스트 방법 | 결과 |
|---|---|---|
| deterministic vs stochastic 액션 차이 | 양쪽 다 stochastic으로 통일 | 동일하게 재현 (기각) |
| 특정 체크포인트의 우연 | 훨씬 이전 체크포인트로 재시도 | 동일하게 재현 (기각) |
| 물리적 좌우 위치(-0.9/+0.9) | 위치를 서로 바꿔서 재시도 | 동일하게 재현 (기각) |
| MuJoCo 컴파일 시 body/geom 인덱스 순서 | XML 선언 순서를 바꿔서 재시도 | 동일하게 재현 (기각) |
| 두 정책 객체가 실제로 같은 가중치인지 | torch.equal로 직접 비교 | 완전히 동일 (기각) |
| 외부 predict() vs 내부 opponent_policy 호출 구조 | a/b를 완전히 같은 호출 방식으로 통일 | 동일하게 재현 (기각) |
| 오래 학습해 굳어진 습관 | 랜덤 초기화부터 완전히 새로 학습 | 1라운드부터 동일하게 재현 (기각) |
| 얼려진 상대(frozen opponent) 구조 자체 | paired self-play로 전면 재구현 | 초반 개선 후 장기 수렴 시 재발 (부분 기각) |
| 신경망이 대칭을 보장 안 함 | 수학적으로 증명된 equivariant 정책으로 재구현 | 여전히 재현 (부분 기각) |
| **관절 부호(양수 vs 음수 토크)가 물리적으로 다르게 안정적** | **정책 없이 상수 토크 +0.3 vs -0.3만으로 최소 재현** | **100% 재현, 부호를 바꾸면 결과도 정확히 역전 → 확인** |

최종 원인은 코드/알고리즘이 아니라 **물리**였다: 이 랙돌은 관절에 양수 토크를 주는 것과 음수
토크를 주는 것이 똑같이 안정적이지 않다(무릎/팔꿈치가 range의 끝에서 시작하는 구조 때문으로
추정). 미러링은 정의상 한쪽엔 원본 부호를, 다른 쪽엔 반전된 부호를 강제하므로, 신경망이 관절
값에 대해 아주 조금이라도 편향을 가지면(그 편향 자체는 3절 18번의 '자발적 대칭 깨짐'으로 생김)
그 편향이 어느 쪽으로 향하든 한쪽은 항상 물리적으로 불리한 부호를 받게 된다. 좌표계를 아무리
잘 대칭화해도(위치를 0 중심으로 두고 관절 부호까지 정확히 반전해도) 이 물리적 비대칭 자체는
좌표계 문제가 아니라서 해결되지 않는다 — 그래서 결국 공유 정책으로 양쪽을 다 잘하게 만드는 접근
자체를 포기하고, P1/P2를 별도 모델로 분리하는 쪽으로 전환했다(3절 21~22번, 2.11절).

이 조사와 별개로, '지금 KO가 왜 이렇게 안 나오나'라는 질문에서 출발한 진단도 있었다: 60판 기준
실제 KO(체력 0)는 0판, 종료 시 평균 체력은 92~99/100로 거의 안 닳아 있었고, 에피소드 길이는 평균
240~270스텝으로 MAX_STEPS(1000)의 27% 정도만 쓰고 낙상으로 끝났다. 즉 KO가 적은 건 'KO에 대한
보상이 약해서'가 아니라 '데미지가 쌓일 시간 자체가 자기 붕괴 때문에 부족해서'로 진단됨 — 여기서도
리워드를 더 세게 주는 것보다 자기 붕괴 문제 해결이 우선이라는 결론.

## 7. 알려진 이슈 / 미해결 과제

- **(진행 중, 개선세) a/b 비대칭 → 리그 셀프플레이로 우회**: self-play에서 'a'가 압도적으로 더 자주
  넘어지는 비대칭의 근본 원인이 결국 물리로 밝혀졌다 — 이 랙돌은 관절에 양수/음수 토크를 주는 게
  똑같이 안정적이지 않고, 미러링은 정의상 한쪽에 항상 원본 부호를, 다른 쪽엔 항상 반전된 부호를
  강제하므로 신경망이 조금이라도 편향되면 한쪽이 구조적으로 불리해진다(3절 19번, 4절). 미러 증강,
  balance/ground/knee 보상, paired self-play, 심지어 수학적으로 증명된 equivariant 정책까지 전부
  이 물리적 비대칭 자체는 못 없앴다. 그래서 "공유 정책 하나가 양쪽 다 잘해야 한다"는 요구를 포기하고
  P1('a' 전용)/P2('b' 전용)을 별도 모델로 리그 학습시키는 방식으로 전환(2.11절) — 각자 자기 역할만
  잘하면 되므로 이 문제 자체가 발생하지 않는다. 초기 라운드에서 학습 순서 자체가 한쪽에 구조적
  이득을 주는 별도 버그를 발견/수정했고(3절 22번), 그 후로는 97:3 → 82:18 → 80:20으로 꾸준히
  좁혀지는 중 — 완전히 50:50까지 수렴하는지는 라운드를 더 지켜봐야 함.
- **자기 붕괴(self-destabilization) 자체**: 상대 접촉 없이 스스로 넘어지는 비율이 여전히 높다.
  PD 밸런스 보조(물리적 해법)가 큰 도움이 됐지만 완전히 해결하진 못했고, ground/knee/balance
  리워드도 뚜렷한 장기 개선을 보여주지 못했다 (위 항목과 사실상 같은 문제의 다른 단면).
- **KO가 거의 발생하지 않음**(측정: 60판 중 0판): 진단 결과 원인은 데미지 보상 부족이 아니라 자기
  붕괴로 인한 조기 종료 — 위 두 항목이 해결되면 자연히 나아질 가능성이 높다는 게 현재 가설, 아직
  검증 전.
- **킥 사용 빈도**: 21:1(펀치:킥)에서 킥 보너스 도입 후 약 9:1로 개선됐으나 완전히 해결되진 않음.
- **DAMAGE_REWARD_SCALE=1.0 및 FORCE_TO_DAMAGE=0.007 재조정**이 장기 학습에서 순효과가 있는지는
  아직 긴 학습 구간으로 검증되지 않음 (짧은 라운드 실험은 노이즈가 커서 결론 확정에 주의 필요).
- **다리(hip/knee) 관절에는 팔과 같은 힘-각도 커브가 아직 없음** — 킥의 회전형 타격이 리워드에
  반영되는 것은 이제 접촉력 재조정으로 확인됐지만(5절), 다리 자체의 근력 커브 적용 여부는 논의만
  되고 미결정 상태.
- **자세를 낮추는(크라우칭) 동작이 기본값처럼 보이는 현상**은 버그가 아니라, 낙상 관련 페널티가
  누적된 상황에서 무게중심을 낮추는 게 안정성 측면에서 합리적인 전략으로 보임 — 별도 조치 없이
  관찰만 된 상태.

### 9.1 매치업/진단 판정 버그 (세션 최대 발견)

7절에서 "a/b 비대칭"으로 계속 언급되던 현상 중 상당 부분이 실은 **측정 버그**였다는 게 드러났다.
`diag_engage.py` 등 거의 모든 진단·매치업 스크립트가 "누가 다운됐나"를 `a_z < FALL_HEIGHT`를
`b_z`보다 먼저 확인하는 if/elif 체인으로 판정하고 있었는데, 두 파이터가 동시에 임계값 근처에
있으면(흔한 상황) 항상 'a' 탓으로 돌렸다. 47%(14/30)가 이 방식으로 오분류됨을 측정으로 확인.

env.py 내부적으로는 처음부터 정확한 `a_out`/`b_out`(health<=0 또는 down_steps>=DOWN_RECOVERY_STEPS)
불리언이 있었지만 `info` 딕셔너리에 노출되지 않아 외부 진단 스크립트들이 자체적으로 부정확한 근사를
다시 구현하고 있었던 것. `info["a_out"]`/`info["b_out"]`을 노출하고 모든 진단/매치업 로직을
이걸 쓰도록 수정 (`matchup_eval.py`는 이 참에 `SubprocVecEnv` 기반 병렬 실행으로도 재작성).
수정 후 같은 체크포인트끼리의 1라운드 매치업이 28:2 → 35:25(58:42)로 정상화됐고, 리그도 그제서야
'b' 학습이 처음으로 트리거됐다.

이 버그는 **학습 자체(내부 종료 판정)에는 영향이 없었다** — 오직 사람이 보는 진단/모니터링
수치만 왜곡시켰다. 그럼에도 세션 초반 "a가 압도적으로 많이 진다"는 인상의 상당 부분이 이 버그
때문이었을 가능성이 크다.

### 9.2 스폰 거리 재검증

측정 버그를 고친 김에 "혹시 거리를 늘리면(1.8) 판정 버그가 아니라 진짜로 서로 접근할 수 있지
않을까"를 처음부터 재학습해서 재검증했다. 결과: 여전히 10% 접근율로 1.2(46.7%+)보다 나쁨 — 먼
스폰 거리 문제는 판정 버그와 무관하게 실재했음을 재확인. `build_model.py`는 -0.6/0.6(총 1.2)로
유지.

### 9.3 발 지오메트리 추가

다리 끝(shin)에 굽은 캡슐 점접촉만 있어 실제 발바닥 역할을 못 했던 것을 발견 — 각 shin 바닥에
발뒤꿈치~발끝 방향 수평 캡슐 geom(`{p}foot_r/l`)을 추가해 실제 지지면을 만들었다.
`_leg_ground_contacts()`도 발 geom과 shin geom 접촉을 명확히 구분하도록 재작성.

### 9.4 자세("주저앉기") 문제 — 페널티 4연속 실패 후 순수 보상으로 해결

7절에서 "관찰만 되고 미해결"이라던 크라우칭 문제를 본격적으로 붙잡았다. 페널티 프레이밍은
**세 번 연속으로 학습을 붕괴시켰다**:

1. 무제한 높이 페널티 → ep_rew_mean -13,000까지 붕괴
2. FALL_HEIGHT 값에서 캡했지만 낙상 구간 내내 0이 아니게 유지 → -7,530까지 붕괴
3. FALL_HEIGHT 아래에서 0으로 죽이도록 수정 → 안정(-679)됐지만 자세 자체는 개선 안 됨
4. 스케일을 1500까지 올린 버전 → -113,000까지 붕괴

원인: 이 페널티들이 넉다운 회복 가능 구간(DOWN_RECOVERY_STEPS, ~150스텝) 동안 이미 걸려 있는
down_penalty/knockdown_entry/terminal 페널티와 겹쳐서 이중·삼중으로 카운트됐다 — 페널티 프레이밍은
"문턱 아래에서 0"이라는 조건 하나만 놓쳐도 이미 등록된 페널티 위에 또 쌓이는 구조적 함정이 있음을
재확인.

최종 해결은 정반대 프레이밍이었다: **머리 높이가 높을수록 좋은, 항상 0 이상인, 제곱으로 급격히
커지는 순수 보상**(사용자 제안).

```python
a_height_reward = HEAD_HEIGHT_REWARD_SCALE * max(0.0, a_head_z / STANDING_HEAD_HEIGHT) ** 2
```

페널티와 달리 이중 카운트될 문턱(cliff)이 없다 — 낮은 값은 그냥 보상이 적을 뿐 escalate하는
페널티가 아니기 때문. 도입 즉시 torso z median 0.54 → 0.92, 크라우칭 비율 0%로 개선 (`scratch23`).

### 9.5 리워드 단순화 (11개 항목 → 4개)

"펀치/킥만 남기고 균형은 height reward가 대신하게 하자"는 제안으로, effort/jerk/balance/down/
knockdown_entry/ground/knee/terminal을 전부 제거하고 **strike / engage / progress / height** 4개
항목만 남겼다 (`progress`는 이 절에서 새로 추가된 항목 — 거리를 좁힌 "행위" 자체에 매 스텝
보상하는 항목, 정적 상태 페널티인 engage와 별개). 종료 조건도 `terminated = a_out or b_out`으로
단순화. 이렇게 나온 `scratch23`이 이 세션 최고 균형점(자세/접근율/안정성 종합) 체크포인트가 됨.

다만 real league 압력(2라운드) 아래에서 height median이 0.92 → 0.71로, 크라우칭 비율이
20.5%로 되돌아가는 걸 관찰 — 4항목 리워드의 개선이 적대적 학습 압력 아래서는 다소 fragile함을
시사 (미해결 관찰).

### 9.6 "정체" 상황 타파 시도 (alive cost) — 실패, 롤백

서로 안 붙고 정체되는 상황을 타파하려 매 스텝 생존 비용(ALIVE_COST)을 페널티로 추가. 0.1, 0.03
두 스케일 다 시도했으나 **둘 다 접근율/자세/안정성 지표를 오히려 악화**시켜 완전히 롤백. "안
싸우면 벌준다"는 직관과 달리, 이 리워드 구조에서는 역효과였다.

### 9.7 다리 폄 게이팅 추가 → 제거 (오진으로 판명)

스켈레톤/슬레드 스포츠의 관성모멘트 비유(사용자 제안 — 사지를 뻗을수록 안정적)로 양 무릎의 평균
굽힘 정도에 따라 root_x 추진력을 게이팅하는 `_leg_extension_scale()`을 추가했었다. height reward
도입으로 크라우칭 방지라는 원래 목적은 이미 중복이 됐고, 오히려 **킥 접촉이 3000스텝 표본에서
0회**로 측정되며 이 게이팅이 킥을 억제하는 부작용이 있다는 가설이 세워져 제거했다. 그런데 제거
후(`scratch26`)에도 킥 접촉이 여전히 0/134이어서 **이 가설은 틀린 것으로 판명** — 진짜 원인은
9.8절에서 밝혀진다.

### 9.8 왜 펀치는 팔만, 킥은 아예 안 나오는가 — 진짜 원인 규명

두 가지 가설을 순서대로 데이터로 검증했다.

**가설 1 (기각): MAX_STEP_DAMAGE 캡이 병목이다.** 캡에 해당하는 raw force는 약 1143N
(MAX_STEP_DAMAGE=8 / FORCE_TO_DAMAGE=0.007). `scratch23`으로 실측한 펀치 접촉력 분포:
median 290N, mean 448N — 캡을 넘는 건 9.9%뿐. 즉 90%의 펀치는 애초에 캡 근처도 안 간다. 캡을
풀어도 최상위 10%만 영향받지, "왜 다들 팔만 까딱거리나"의 답은 아니었다.

**가설 2 (확인): height reward가 strike reward를 압도한다.** 같은 롤아웃에서
`info["reward_breakdown"]`을 항목별로 누적 합산했더니:

| 항목 | 에피소드당 합계 (scratch23) |
|---|---|
| height | +617.4 |
| engage | -169.3 |
| strike (net) | -4.9 |
| progress | ~0 |

height가 strike보다 자릿수로 100배 가까이 크다. 균형을 걸고 더 세게/다리로 때리는 선택은 기대값상
완전히 손해인 구조 — 캡이 아니라 **보상 스케일 불균형**이 진짜 원인이었다. (참고: root_ry가 RL
행동 공간에 없다는 2.3절의 구조적 제약도 부차적 요인으로 작용 — 정책이 애초에 허리를 돌려 체중을
싣는 동작 자체를 할 수 없음.)

**대응 실험 (`scratch27`, `scratch23`에서 이어 학습, DAMAGE_REWARD_SCALE 3.0 → 10.0):**

| 지표 | scratch23 | scratch27 (scale 10.0) |
|---|---|---|
| 킥 접촉(6000스텝) | 0 | 36 |
| 펀치 접촉(6000스텝) | 142 | 221 |
| 펀치 median force | 290N | 123N |
| 자세(torso z median) | 0.92 | 0.565 |
| 스크립트봇 낙상률 | 16.7% | 13.3% |
| 실전 접근율(foot_dist≤1.0) | 66.7% | 40.0% |
| 실전 낙상률 | ~23% | 36.7% |

킥은 드디어 나왔지만(개별 타격력을 올리기보다는 "더 자주, 가볍게" 때리는 쪽으로 반응), 자세가
다시 무너지고(9.4절에서 어렵게 잡은 문제 재발) 접근율이 크게 떨어지며 실전 낙상률도 올랐다. "덜
붙고 더 조심하는 아웃복싱 아니냐"는 재해석도 검토했으나, 진짜 아웃복싱이면 낙상률이 낮아져야
하는데 오히려 올랐다는 점에서 기각 — 안정성 자체의 악화로 판단. 이는 과거 3절 5번 항목에서
DAMAGE_REWARD_SCALE=5.0이 (구 11항목 리워드 체제에서) engagement를 86.7%→63.3%로 떨어뜨렸던
것과 같은 패턴이 4항목 체제에서도 재현된 것으로 보인다 — 다만 이번엔 훨씬 큰 배율(10.0)에서
터졌다는 차이가 있어, 더 낮은 배율(5.0~6.0)에서 절충점을 찾는 실험이 다음 단계로 진행 중.

### 9.9 P1/P2 격차 원인 조사와 ent_coef 폭주 사고

리그를 재개해 40라운드를 돌린 결과, 22라운드 이후로 P1이 P2에게 구조적으로 계속 밀리는 현상을
발견했다 (round 38엔 20:3까지 벌어짐). 원인은 두 가지가 겹친 것으로 확인됐다.

**직접 원인**: `selfplay_league_dynamic.py`는 원래 `--max-consecutive` 기본값을 2로 낮게 잡아뒀고
(같은 얼려진 상대로는 1라운드 후 개선이 정체된다는 실측 코멘트가 스크립트에 이미 있었음), 그런데
리그를 재개할 때 `auto_pipeline.py`의 예시값을 그대로 복사해 `--max-consecutive 15`를 줘버렸다.
그 결과 P1이 같은 P2 체크포인트를 상대로 15라운드(15M 스텝) 연속 학습됐다.

**메커니즘**: `train_league.py --init-from`은 매 라운드 같은 PPO 옵티마이저 상태를 이어가므로, SB3
PPO의 기본 `ent_coef=0.0`(엔트로피 보너스 없음) 하에서 정책의 행동 표준편차(std)가 라운드를 거듭할
수록 단조 감소했다 — round 1의 0.489에서 round 37엔 0.0248까지, 거의 결정론적 정책으로 수렴. 같은
상대에게 15라운드나 몰아서 학습시키니 이 좁아진 정책이 그 상대에게만 과적합되며 일반화 능력을
잃었고, 결과적으로 "더 학습시켰는데 더 진다"는 역설적 현상으로 나타났다.

**1차 대응(실패)**: `train_league.py`에 이미 있던 `--ent-coef` 오버라이드 기능을
`selfplay_league_dynamic.py`에 새로 연결해 `--ent-coef 0.01`로 100라운드를 재실행했다. round1
초반엔 std가 0.0602→0.0621로 회복 방향을 보여 성공한 것처럼 보였으나, **std를 누르는 상한이 전혀
없어서 엔트로피 보너스를 더 받으려는 그래디언트가 계속 std를 키우는 쪽으로 폭주**했다 — round
24 무렵 이미 90~100대, 100라운드 종료 시점엔 **1.11e16**까지 도달. 최종 체크포인트의 log_std를
직접 확인하니 10개 행동 차원 중 9개가 log_std ~31~37(사실상 무한 분산)로, head 관절 하나만 정상
작동하고 나머지는 전부 ±1 랜덤 노이즈였다. 이 100라운드 동안 관찰된 "균형 잡힌" 매치업(예:
round 91 8:8, round 97 8:8)은 실력이 좋아진 게 아니라 **양쪽 다 노이즈로 붕괴해서 우연히 비슷한
빈도로 자빠진 것**이었다 — 전체 결과 폐기.

**교훈**: PPO의 log_std는 상한이 없는 학습 가능한 파라미터라, 양의 `ent_coef`는 엔트로피가 낮을 때
붕괴를 막아주지만 그 자체로 폭주를 막는 장치가 없다. 나중에 다시 시도한다면 std 상한 클리핑이나
주기적 모니터링(임계값 넘으면 자동 중단) 같은 안전장치를 반드시 같이 넣어야 한다.

**최종 대응**: `ent_coef` 오버라이드 없이(SB3 기본값 유지), `--max-consecutive`만 스크립트 원래
기본값(2)으로 되돌려서, std가 아직 정상이던 round 21/22 체크포인트(`ppo_p1_20260819_023117.zip`
/ `ppo_p2_20260819_023625.zip`)로 롤백해 재시작.

## 10. 자세/균형 리워드 재설계, 두 번째 폭주 사고, from-scratch 재학습

### 10.1 낙상 원인 실측: 맞아서가 아니라 스스로 무너짐

"낙상이 펀치에 밀려서인가 피하다 넘어지는 건가"라는 질문에서 출발해, 낙상 시점 직전 15스텝 안에
피격이 있었는지를 직접 계측했다 (`/tmp/diag_fall_cause.py` 계열, 36개 낙상 이벤트 표본). 결과:
**86.1%(31/36)가 직전 피격 없이 스스로 무너진 것**이었고, 피격 직후 낙상은 13.9%(5/36)뿐이었다.
7절/4절에서부터 계속 언급되던 "자기 붕괴(self-destabilization)"가 세션 막바지까지도 여전히
지배적인 원인이라는 게 재확인됐다.

### 10.2 다리를 벌려 균형 잡지 않는 이유

"걷는 자세처럼 다리를 벌려서 균형을 잡으면 안 되나"라는 질문에 대해 실측으로 답했다. 이 모델은
완전히 2D(시상면, XZ 평면)라 다리를 좌우로 벌리는 것 자체가 물리적으로 불가능하고(양쪽 힙 관절
축이 둘 다 앞뒤 회전만 함), 가능한 건 한쪽 다리를 앞으로 다른 쪽을 뒤로 빼는 앞뒤 스탠스뿐이다.
측정 결과 발 사이 간격 median=0.025m(거의 항상 다리를 붙임), p90=0.681m(가끔 크게 벌어짐 —
주로 킥/펀치 동작의 부산물)로, 안정적인 방어 자세로 정착시키진 않고 있었다. 원인은 (1) height
reward가 머리 높이만 볼 뿐 다리 간격(지지 기반)은 전혀 안 보고, (2) 몸통이 앞뒤로 기울어지는 걸
막는 메커니즘 자체가 다리 위치와 무관한 별도의 PD 보조(2.3절)라서 "다리를 벌리면 덜 넘어진다"는
직접적 물리적 인과가 약하기 때문으로 추정.

### 10.3 height reward 재설계: 캡 + stability 보너스

height reward가 `ratio^2`로 상한이 없어서 "최대한 뻣뻣하게 서있기"가 항상 더 유리한 구조였다
(실제 복서의 약간 굽힌 준비 자세보다 꼿꼿한 자세가 보상상 우위). 두 가지를 추가:

- **HEAD_HEIGHT_RATIO_CAP = 1.0**: `ratio`를 1.0에서 캡. 정상 서있는 높이에 도달하면 그 이상
  뻗어도 추가 보상이 없어, 넘어짐 회복 그라디언트는 그대로 두면서 "과도한 신장" 유인만 제거.
- **STABILITY_REWARD_SCALE**: `root_ry` 각속도(`qvel`, 몸통이 얼마나 빨리 기울어지는 중인지)가
  낮을수록 보상. `max(0, 1 - |ry_vel|/RY_VEL_REF)^2` 형태로 height reward와 같은 캡-프리(cliff-free)
  설계. 처음 스케일 0.5로 실측했더니 에피소드당 합계가 strike(122.7)의 3배(393.6)나 돼서, height가
  strike를 압도했던 9.8절의 실수를 반복할 뻔했다 — 0.15로 낮춰 strike와 비슷한 자릿수(82.6)로
  맞춤. root_ry 각속도는 전진(root_x)이나 팔다리 공격 동작 자체와는 무관해서(직접 제어하는
  관절이 아님), "가만히 있어야 유리하다"는 유인은 이론상 없지만, 타격 반작용으로 몸통이 흔들리면
  공격을 회피하려는 간접 유인이 생길 위험은 있어 향후 지켜봐야 함.

이 리워드는 학습 전 규모를 실측하고 조정한 뒤 곧바로 학습(resume)에 반영했다 — 처음부터 다시
학습할 필요는 없다고 판단(미세조정 성격의 변경이라 기존에 배운 전투/접근 능력을 재사용하는 게
효율적)했으나, 10.5절에서 결국 이 판단을 뒤집게 된다.

### 10.4 P1/P2 격차 재발과 두 번째 std 폭주 사고 (엔트로피 계수)

height 캡 + stability 보너스를 반영한 채로 리그를 재개했다. 이 과정에서 사용자가 "모델 자체에
다양성을 부여할 수는 없냐"고 물어, 9.9절에서 이미 확인된 "std가 라운드를 거듭할수록 계속 줄어드는"
문제(SB3 PPO 기본 `ent_coef=0.0`, 즉 엔트로피 보너스가 아예 없어서 std가 학습이 누적될수록 계속
줄기만 함)에 대한 대응으로, `selfplay_league_dynamic.py`에 `--ent-coef` 옵션을 새로 연결해
(`train_league.py`엔 이미 있었지만 리그 루프에 안 물려 있었음) `--ent-coef 0.01`로 100라운드를
실행했다.

round 1 초반엔 std가 0.0602→0.0621로 회복되는 것처럼 보였으나, **std를 누르는 상한이 전혀 없어서
엔트로피 보너스를 더 받으려는 그래디언트가 계속 std를 키우는 쪽으로 폭주**했다 — round 24 무렵
이미 90~100대, 100라운드 종료 시점엔 **1.11e16**까지 도달. 최종 체크포인트의 log_std를 직접
확인하니 10개 행동 차원 중 9개가 log_std ~31~37(사실상 무한 분산)로, head 관절 하나만 정상 작동
하고 나머지는 전부 ±1 랜덤 노이즈였다. 이 100라운드 동안 관찰된 "균형 잡힌" 매치업은 실력이
좋아진 게 아니라 양쪽 다 노이즈로 붕괴해서 우연히 비슷한 빈도로 자빠진 것이었다 — 전체 결과 폐기.
(9.9절의 첫 번째 사고와 사실상 같은 실수의 재발: `ent_coef`라는 안전한 것처럼 보이는 레버도
상한 없이는 위험하다는 교훈이 한 번 더 확인됨.)

`ent_coef` 오버라이드를 완전히 제거하고 `--max-consecutive=2`만 유지한 채, height 캡 + stability
보너스가 반영된 시점의 체크포인트로 롤백해 재시작.

### 10.5 대시보드 지표 확장 (라운드별 자세/타격/KO/std)

사용자 요청으로 리그 라운드별로 다음 지표들을 대시보드에 추가:

- **매치업 판당 KO 카운트**: `matchup_eval.py`가 이미 계산하던 `end_reason_counts`를 로그에
  같이 남기도록 `selfplay_league_dynamic.py` 수정.
- **자세(머리높이비율) / 안정성(std)**: `env.py`의 `info`에 `a_head_z`/`b_head_z`를 새로 노출하고,
  `matchup_eval.py`가 매치업 평가차 이미 돌리는 롤아웃에 무임승차해서 평균을 같이 계산
  (`mean_head_ratio_a/b`) — 별도 연산 비용 없음. std는 각 라운드 학습 서브프로세스가 이미
  stdout에 찍는 SB3 로그(`|    std    | ... |`)를 라운드 학습 직후 로그 파일에서 되짚어 파싱.
  9.9/10.4절의 폭주 사고 이후로 이 std 추적이 조기 경보 역할을 하도록 대시보드에 상시 표시.
- **타격수**: 새 API 호출 없이, `info["reward_breakdown"]["strike"]`의 부호(+면 a가 방금 맞힘,
  -면 b가 방금 맞힘)로 신규 접촉 여부를 추론 — 이미 계산되는 리워드 항목을 재사용.
- 처음엔 타격/KO 비율(%)을 별도 패널로 뺐다가, 사용자 요청으로 비율 대신 **원시 카운트**로
  바꾸고 별도 패널을 없애서 기존 "리그 라운드별 매치업" 차트 하나에 P1/P2 패배·KO·타격수를 전부
  합쳤다 (y축을 episodes 고정이 아니라 데이터 중 최댓값에 맞춰 동적으로 스케일).

이 지표들이 전부 매치업 평가 시점에 하는 단일 롤아웃에서 나오므로, 리그 학습 자체의 연산량은
전혀 늘지 않는다.

### 10.6 재발한 "뻣뻣한 자세" — resume 대신 from-scratch로 전환

height 캡 + stability 보너스를 적용한 채로 리그를 재개했음에도, 실제 시뮬을 육안으로 보니 여전히
"일자로 굳은" 자세가 남아있었다. 리워드 변경이 미세조정이라 resume이면 충분하다고 판단했던
10.3절의 결론을 사용자가 뒤집어, **`ppo_fresh1`이라는 이름으로 완전히 새로 랜덤 초기화부터
학습**을 시작했다 (`train.py`, `--resume-from` 없이, 스크립트 상대로 10M 스텝).

10M 스텝 종료 후 진단: torso z median 0.632, 스크립트 봇 상대 낙상률 20%(6/30) — 기존 resume
체인들의 뻣뻣한 자세(scratch23 기준 0.92)보다 낮고 자연스러운 편. 이 체크포인트를 P1으로 삼아
P2를 부트스트랩(`train_league.py --side b`, 자기 자신 상대로 1M 스텝)하고, 초기 매치업(4:14)을
확인한 뒤 리그를 처음부터 재시작했다 (`--max-consecutive=2`, `ent-coef` 없음).

밤새(약 6시간, 72라운드) 무인으로 돌린 결과:

- **자세**: 머리높이비율이 라운드 내내 0.65~0.70 범위로 안정적 유지 — 뻣뻣했던 resume 체인과
  달리 자연스러운 범위에 정착. 원래 문제였던 "일자 자세"는 이 lineage에서 해결된 것으로 보임.
- **std**: 0.026~0.03 근방에서 안정, 폭주도 붕괴도 없음 — `max-consecutive=2` + `ent_coef` 미사용
  조합이 두 번의 사고(9.9, 10.4) 이후로는 안전하게 작동하고 있음을 실측으로 확인.
- **P1/P2 균형**: P1이 타격수에서 전체적으로 P2보다 약 2.5배 앞섬(전반부 평균 250:88, 후반부
  206:82로 하락은 했지만 여전히 우세). 패배 수 격차는 좁혀지는 추세(전반부 P1-P2 패배차 -2.7 →
  후반부 -1.1) — 아직 50:50은 아니지만 점진적으로 균형을 찾아가는 중.

리그는 100라운드 목표로 계속 진행 중이며, 균형이 완전히 수렴하는지는 이후 라운드에서 계속
확인이 필요하다.

### 10.7 낙상 원인 재조사: 회전이 아니라 "똑바로 선 채로 가라앉음"

79라운드까지 돌린 결과 낙상률이 68~71%에서 전혀 안 줄어드는 걸 확인한 뒤(10.6절 이어서), 원인을
더 정밀하게 재조사했다. 낙상 이벤트 직전 20스텝의 `root_ry`(몸통 회전각)와 `root_ry` 각속도,
무릎 각도, 몸통 z를 직접 추적한 결과:

- **22건 중 22건(100%) 회전(tipping)이 아니었다** — 낙상 순간 `|root_ry|` median 0.024 rad
  (~1.4도)로 거의 안 기울어짐.
- 낙상 직전 20스텝 동안 무릎 각도도 거의 안 변함(median 변화량 -0.001) — 무릎이 갑자기 꺾이는
  것도 아님.
- 근데 그 20스텝 동안 몸통 z는 median 0.161m 뚝 떨어짐.

즉 "넘어짐"이 아니라 **똑바로 선 자세 그대로 가라앉는** 패턴이었다. 결정적으로, `root_z`(몸통
높이 축)는 `build_model.py`에 액추에이터가 아예 없는 순수 slide 조인트다 — 다리의 지면 반력에
전적으로 의존하는 수동적 결과라서, 일단 지지가 실패하면 정책이 `root_ry`를 통해 이걸 직접 막을
방법이 없다. 이게 10.3절의 `STABILITY_REWARD_SCALE`(root_ry 각속도 기반)이 79라운드 내내
낙상률에 전혀 효과가 없었던 이유였다 — 애초에 엉뚱한 축을 겨냥하고 있었다.

대응으로 stability 보상을 `root_z` 하강 속도 기반으로 다시 설계했다(`Z_VEL_REF=1.0`, 마찬가지로
cliff-free 캡 형태). 100라운드를 새로 돌렸지만 **이것도 낙상률을 못 줄였다** — 초반엔 59.7%로
시작했다가 학습이 진행될수록 오히려 68% 근방으로 수렴, 이전 버전과 사실상 같은 지점에 도달했다.
같은 시기에 시도한 다리 벌림(`stance`, 발 간격에 캡 씌운 보상)도 마찬가지로 실패했다 — 발 간격
자체는 median 0.002m→0.190m로 실제로 벌어졌는데도 낙상률은 오히려 73→80%로 더 나빠졌다. 세
번의 리워드 시도(회전 stability, 하강속도 stability, 다리벌림 stance) 전부 실패.

### 10.8 물리 개입: 발 지오메트리 — 각진 발은 대실패, 굵은 캡슐은 대성공

리워드로 안 풀리자 물리 자체를 바꿔봤다. 사용자 제안으로 "접지면 확대"를 시도:

**1차 시도: 캡슐 발 → 박스(평평한 밑창) 발.** 헬스케어 접지 면적을 키우자는 취지로 발 geom을
box(size 0.095×0.05×0.02)로 바꾸고 처음부터 재학습(`ppo_fresh2`, 10M 스텝). 결과는 **대실패**
— 100라운드 평균 낙상률이 **90.3%**까지 치솟았다(기존 캡슐 발 68% 대비 오히려 22%p 악화). 원인
추정: 박스는 모서리가 있어서 발이 살짝만 기울어도 한쪽 모서리가 먼저 닿으며 갑작스러운 토크가
튀는 "모서리 걸림" 현상이 생긴다 — 실제 로봇공학에서 각진 발보다 둥근 발이 제어하기 쉬운 것과
같은 이유. 캡슐(둥근 표면)은 어떤 각도로 닿아도 부드럽게 구르며 접촉하지만 박스는 그렇지 않다.

**2차 시도: 캡슐 유지, 반지름만 2배 확대(0.035→0.07).** 모서리 문제를 피하면서 접지 여유(허용
오차)만 키우자는 절충안. 처음부터 재학습(`ppo_fresh3`). 결과는 **뚜렷한 개선**:

| 지표 | 얇은 캡슐(기존) | 박스 | 굵은 캡슐(fresh3) |
|---|---|---|---|
| 스크립트봇 낙상률 | ~17~20% | - | **3.3%** |
| 리그 낙상률(전체) | 68% (정체) | 90.3% | **36.4~44.2%** |
| 리그 낙상률(초반 10라운드) | ~60% | ~83~90% | **~47%, 계속 하락** |

리워드로 세 번 실패한 문제를, 물리(발 반지름) 하나로 거의 절반 수준까지 낮췄다 — 이 세션에서
가장 확실하게 먹힌 단일 개입이었다.

`ppo_fresh3` 100라운드를 마저 돌린 뒤 낙상 이벤트를 다시 재보니(10.7절과 같은 방법론), 이번엔
패턴이 달라져 있었다: `root_ry` 여전히 거의 안 움직이지만(회전은 여전히 아님), **무릎이 낙상
직전 20스텝 동안 실제로 눈에 띄게 더 굽음**(median knee_drop=0.277, 낙상 시점 무릎각
median=-1.17) — "갑자기 지지력을 잃고 가라앉는" 패턴에서 "무릎이 하중을 못 버티고 서서히
꺾이는" 패턴으로 바뀌었다. 발 문제는 풀렸지만 다리 힘(액추에이터) 문제가 남아있다는 신호로
해석, 다음 실험으로 이어짐.

### 10.9 다리 힘(gear) 실험: 힘만 올리면 역효과, damping도 같이 올려야 함

10.8절 마지막 진단(무릎이 하중을 못 버팀)에 따라 hip/knee 액추에이터 gear를 50% 올렸다
(hip 60→90, knee 40→60). 처음부터 재학습(`ppo_fresh4`).

**결과는 역효과였다.** 스크립트봇 상대 낙상률은 0%로 좋아 보였지만, 실제 리그(자기 자신 상대)
에서는 10라운드 내내 77~93%(평균 85.7%)로 fresh3의 초반 추세(47%→계속 하락)와 정반대로 전혀
개선되지 않고 오히려 최근 라운드가 더 나빴다.

원인으로 지목한 것: **gear만 올리고 관절 damping(=2)은 그대로 뒀다.** 토크는 세졌는데 제동력은
그대로라 관절이 더 튀고 오버슈트하기 쉬워졌을 것으로 추정 — 힘은 세지만 그만큼 정교하게 제어하는
법은 아직 못 배운 상태에서, 더 격렬하고 다루기 힘든 움직임만 만들어낸 셈. gear를 1.5배 올렸으니
damping도 같은 비율로 올려서(2→3) 재검증(`ppo_fresh5`, 처음부터 재학습).

**결과: 이번엔 성공적이었다.** 초기 리그 매치업 낙상률 3.3%(1/30), 이후 첫 12라운드 평균
33.1%(구간별 20~50% 사이 변동, 노이즈 있지만 fresh3보다도 안정적으로 낮은 편) — KO율도
17~23%까지 올라 낙상보다 실제 타격으로 승부가 나는 비중이 늘었다. gear를 올리는 것 자체가
문제가 아니라, damping과 짝을 맞추지 않은 게 문제였다는 가설이 실험으로 뒷받침됨.

### 10.10 무릎 접지 회피 보상 재도입 (이진 → 연속형)

시뮬을 육안으로 보니 여전히 "무릎 꿇는" 자세가 자주 보여, 예전에 있다가 4항목 단순화(9.5절)
때 삭제됐던 knee 보상을 다시 붙였다. 계산 자체(`_leg_ground_contacts`, 발 geom vs 정강이 geom
접촉 구분)는 죽은 코드로 남아있어 그대로 재사용 가능했다.

**1차: 접촉 여부(0/1/2, 이진) 기반.** `KNEE_AVOID_SCALE * (1 - knees_down/2)` 형태로 리워드에
추가. 사용자가 바로 짚은 문제: 접촉이라는 이진 신호는 **닿는 순간까지 아무 경고 신호가 없다** —
height/stability처럼 "가까워질수록 서서히 나빠지는" 연속적 그라디언트가 없어서, 닿기 직전
상태들에 대한 학습 신호가 약함.

**2차: 무릎 관절의 지면으로부터의 실제 높이(연속값) 기반으로 재설계.**
`self.data.xanchor[knee_joint_id][2]`로 각 무릎의 월드 z좌표를 직접 읽어, height reward와 같은
캡 형태로 변환:
```python
a_knee_avoid_reward = KNEE_AVOID_SCALE * min(1.0, max(0.0, a_min_knee_z / KNEE_HEIGHT_REF)) ** 2
```
양쪽 무릎 중 **최솟값**(더 위험한 쪽)을 기준으로 삼아, 한쪽만 낮아져도 다른 쪽이 높다고 신호가
묻히지 않게 함. `KNEE_HEIGHT_REF=0.4`는 정상 서있는 상태의 실측 median(~0.41m)에 맞춤. 학습 전
`strike` 대비 규모를 실측(per_ep 26.7 vs strike 136.6)해 과도하지 않음을 확인 후 반영, 리그를
이어서(resume) 재시작.

### 10.11 서버 재부팅 사고

`ppo_fresh3` 학습 도중 서버 자체가 재부팅되는 사고가 있었다(`uptime`으로 가동시간이 재부팅
시점과 정확히 일치함을 확인 — 내 프로세스 문제가 아니라 인프라 이벤트). nohup으로 띄운 모든
백그라운드 프로세스(학습, 대시보드)가 함께 죽었고, 재부팅 도중 쓰던 autosave 체크포인트 여러
개가 0바이트로 손상됐다. 손상되지 않은 가장 최신 체크포인트(파일 크기 확인)를 찾아 그 지점부터
`--resume-from`으로 이어서 학습을 재개해 큰 손실 없이 복구했다. `/tmp` 스크래치패드의 진단
스크립트들도 재부팅으로 날아가 여러 번 재작성해야 했다.

### 10.12 현재 상태 (이 절 작성 시점)

- 물리: 발 = 굵은 캡슐(반지름 0.07), hip/knee gear 90/60(기존 60/40에서 상향), 관절 damping 3
  (기존 2에서 상향)
- 리워드: strike / engage / progress / height(1.0 캡) / stability(root_z 하강속도 기반) /
  stance(발 간격) / knee_avoid(무릎 높이, 연속형) — 7항목
- `ppo_fresh5` lineage로 리그 진행 중, 낙상률 20~40%대(노이즈 있음)로 세션 시작 시점 대비 크게
  개선됐으나 완전히 해결된 건 아님. P1/P2 균형과 "무릎 꿇는" 시각적 연출이 완전히 사라졌는지는
  추가 라운드로 계속 확인 필요.
